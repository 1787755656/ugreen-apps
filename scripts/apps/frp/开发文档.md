## 一、架构总览

### 进程模型

```
systemd (UGOS 平台, Restart=on-failure, 探活 :28600)
  └─ bin/frp-mgr --port=28600        ← Go 管理壳(start_cmd 直启,无 sh 包装)
       ├─ 守护 goroutine: frps  ── spawn/守护 ── bin/frps -c <data>/frps.toml
       ├─ 守护 goroutine: frpc  ── spawn/守护 ── bin/frpc -c <data>/frpc.toml
       └─ HTTP :28600  管理页(内嵌单文件) + /api/*
```

- 平台停止 = SIGTERM → 10s → SIGKILL;壳收到 SIGTERM 先温和停两个子进程再退出。
- 探活打的是壳自己的端口,frpc/frps 没起不影响"启动成功"判定。

### 关键设计决策(为什么是这样)

| 决策 | 理由 |
|---|---|
| `inner` 形态(2026-11-07 从 tab 切回) | 用户要的是"桌面里点开就在内嵌窗口",不要另开浏览器标签。原先选 tab 的唯一理由是本应用自持 Cookie 会话、进 inner 会因网关压 `SameSite=Strict`(PC 客户端还整体拒收第三方 Cookie)导致登录回环 —— 现在会话改成**登录下发 token、前端走 `Authorization: Bearer`**,Cookie 只是兼容旁路,这个理由不再成立 |
| 出厂密码 `frpadmin`(不再随机) | 随机密码要求用户先去数据目录翻 `凭据说明.txt`,手机端根本翻不到;固定密码写进应用简介,装上即可登录,登录后页面顶部常驻提醒条直到改掉密码 |
| 自持密码登录(不接 UGOS 网关身份) | 管理页是"配 frp 隧道"的独立安全域,与 NAS 账号解耦更省事(多用户 NAS 上不必给每个账号开管理权);CLIProxyAPI/musicsub 同款先例 |
| 无 EXEC 权限 | start_cmd 直启二进制、壳只 exec 包内二进制,启动链上没有 sh |
| 仅 `NETWORK.ACCESS_INTERNET` | 默认 unit 只放私网:frpc 连公网服务端、frps 被公网客户端连入都会被 `IPAddressDeny=any` 废掉,必须声明;声明后 IP 过滤整个消失 |
| 管理壳钉 go1.26 线编译 | 固件 systemd `DefaultEnvironment` 注入 `GODEBUG=tlskyber=0`,go1.27+ 编译的二进制启动即 fatal(1.26.x 可活,natfrp 实证);子进程 env 另做消毒(见下) |
| frps/frps 配置放 data 目录 | 安装目录只读;升级不丢配置 |
| 双服务默认停用 | frpc 首启就乱连/监听有风险;用户在页面里改好配置再启用 |

### 端口规划

| 端口 | 用途 | 备注 |
|---|---|---|
| 28600 | 管理壳(探活) | 避开上游默认 7000/7500 与常见占用 |
| 7100 | frps 默认 `bindPort` | 上游默认 7000 往高位挪一档(防与用户已装 Docker 版 frp 撞) |
| 7500 | frps 可选 dashboard | 模板里注释着,启用后局域网直接可达,模板里提醒设强密码 |

### 数据目录布局(`$UGAPP_DATA_DIR`)

```
manager.json     管理壳状态:PBKDF2 盐/哈希、HMAC 会话钥、双服务启用开关、password_is_default 标志(0600)
凭据说明.txt     出厂密码 frpadmin + 忘记密码的恢复办法(仅首启生成)
frps.toml        服务端配置(缺文件时自动补默认模板)
frpc.toml        客户端配置(同上)
log/  → 实际落在 $UGAPP_LOG_DIR: frpc.log / frps.log(子进程 stdout+stderr 追加)
cache/tmp/       TMPDIR(沙箱没有 /tmp)
```

## 二、管理壳实现(monorepo `scripts/apps/frp/launcher/`,纯标准库)

### 文件职责

| 文件 | 职责 |
|---|---|
| `main.go` | 启动、目录解析(`UGAPP_*` 带兜底)、默认模板(双模板**共享同一随机 token**)、frp 版本探测(`frpc -v`)、路由注册、SIGTERM 优雅退出 |
| `store.go` | `manager.json` 读写(原子写 tmp+rename)、PBKDF2 密码(出厂默认 `frpadmin`)、HMAC 无状态会话、登录限流、令牌生成 |
| `proc.go` | `Svc` 守护循环、`stopProc`(SIGTERM→超时→SIGKILL)、`verifyConfig`、`tailLines`、`ChildEnv`(GODEBUG 消毒+TMPDIR) |
| `api.go` | HTTP 路由、会话中间件(Cookie 或 Bearer 令牌)、`writeGuard` 写接口防线、`/api/diag` 本机闸、JSON 工具 |
| `www/index.html` | 前端单文件(vanilla JS,go:embed 内嵌**并同步到 rootfs_common/www**),零外部依赖、无 SW、全 addEventListener 无 inline handler;登录拿 token 存 localStorage,请求带 `Authorization: Bearer` |
| `store_test.go` | 单测:密码往返/重开不重置/损坏重初始化/会话篡改与过期/限流锁定/密码字符集 |

### 首启时序

`resolveDirs`(mkdir + `TMPDIR`→cache/tmp) → `loadOrCreateStore`(用出厂密码 frpadmin 生成 salt/hash + session key,置 `password_is_default=true`) → `writeCredentialsFile`(凭据说明.txt) → `writeDefaultConfigs`(**两份模板共用同一个 token**,出厂即可互连) → `detectFrpVersion` → 启动双守护循环(按持久化 enabled 拉起) → HTTP 就绪。

### 认证设计(参数备查)

- 密码:PBKDF2-HMAC-SHA256,120000 轮,16B 盐,32B 长;比较走 `subtle.ConstantTimeCompare`。改密码需会话 + 旧密码,新密码 ≥8 位;**改密码会落盘**(`setPassword` 里 `saveLocked`,早期版本漏了这句,重启后密码会回滚);改密码不掉会话(session key 不换)。
- 会话:无状态 HMAC token = `hex(过期unix时戳,BE 8B) + "." + base64url(HMAC-SHA256(sessionKey, 时戳8B))`,TTL 30 天。**两条取值路径**:`Authorization: Bearer <token>`(inner 主通道)与 Cookie `frpmgr_session`(直连 28600 / 同源网页)。**重启不掉线**(key 持久化)。
- Cookie 属性按入口自适应:请求来自 HTTPS(`r.TLS != nil` 或 `X-Forwarded-Proto: https`)→ `SameSite=None; Secure`,否则 `Lax`。写死任一个都会在 iframe 里"登录了但一直 401"。
- 限流:按源 IP,连续 5 次失败锁 60s(内存 map,重启即清)。
- CSRF:写接口(POST)走 `writeGuard` —— Origin 与 Host(或 `X-Forwarded-Host`)主机名一致即放行;不一致时**只认请求头里的令牌,不认 Cookie**(Cookie 在 `SameSite=None` 下会被跨站请求带上,认它等于没防护)。登录接口不卡 Origin(网关可能改写 Host,卡死等于整个应用打不开;而登录 CSRF 得先知道密码,收益为零)。
- `/api/diag` 按标准做法只对 NAS 本机源 IP 开放(回环或任一本机网卡地址)。
- `/healthz` 完全开放只回 `ok`;页面 `/` 开放但**不含任何业务数据**(配置全走鉴权 API,401 时前端渲染登录框)。

### 守护循环状态机(per 服务一个 goroutine)

```
enabled==false → 阻塞等 ch 信号
enabled==true  → launch(exec, 子进程 env=ChildEnv(), cwd=dataDir, stdout/stderr→log 追加)
                 → wait → 退出分类(terminated/killed = 优雅,清 lastErr;否则记 lastErr)
                 → enabled? 退避后重启(2s 起步 ×2,上限 30s;运行满 3 分钟重置)
                 : 回到等待
enable: 写 manager.json + 信号; disable: 写状态 + stopProc(6s)
restart: stopProc(6s) + 信号(API 层先 verify,失败拒绝重启)
```

注意:frps 改配置**不会热加载**——重启后生效;frpc 默认 `loginFailExit`,连不上/密钥错会主动退出,由守护循环按退避拉起,表现为"进程在运行/退出之间反复"是正常现象,修好配置重启即恢复。

### `verifyConfig` 与配置保存

- 保存:内容非空 → 原子写 `frps/frpc.toml`(0600) → `bin/frpc|frps verify -c <cfg>`(15s 超时,输出截断 4000 字符)→ 回 `{written, verify_ok, verify_out}`。**保存总是落盘**,校验结果只作提示;启用/重启路径校验失败则拒绝执行。
- 启用时若配置文件缺失 → 自动补默认模板(`writeDefaultConfigs(false)`,保持 token 成对)。

### 日志

- 子进程 stdout+stderr 追加写 `$UGAPP_LOG_DIR/frpc|frps.log`;守护循环事件以 `[管理壳]` 前缀写同一文件(网页日志视图能看到生命周期)。
- `tailLines`:从文件尾最多读 512KB,取末 N 行(默认 200,API 上限 1000);**剔除 NUL 字节**(flx86 virtiofs 对正被写入的文件会读出 NUL 垃圾段,真机 ext4 无此层,但剔了无副作用)。

### ChildEnv(GODEBUG 消毒)

```go
// 固件 systemd DefaultEnvironment 注入 GODEBUG=tlskyber=0,go1.27+ 二进制见之即 fatal。
// 剥掉 GODEBUG 与 TMPDIR,重指 TMPDIR=cache/tmp。
```

frp 0.71.1 是 go1.26.8 编的,本就无害;消毒是防**上游未来换 1.27 工具链**(natfrp 2026.10.23 同款事故)。管理壳自身:monorepo build.sh 钉 go1.26.6 + `GOTOOLCHAIN=local`。

### API 清单

| 方法/路径 | 鉴权 | 说明 |
|---|---|---|
| GET /healthz | 无 | 探活,只回 `ok` |
| GET / · /favicon.ico | 无 | 单页应用(无业务数据)/图标 |
| POST /api/login | 限流+Origin | `{password}`,成功种 Cookie |
| POST /api/logout | 无 | 清 Cookie |
| GET /api/diag | 仅本机源 IP | 自查:版本/路径/文件存在性/调用方头;**不回显任何密钥** |
| GET /api/status | 会话 | 壳版本/frp 版本/双服务 {enabled,running,pid,since,last_err} |
| GET /api/config?svc= | 会话 | `{svc,path,content}` |
| POST /api/config | 会话+Origin | `{svc,content}` → 保存+verify 结果 |
| POST /api/service | 会话+Origin | `{svc,action:enable/disable/restart}`;restart 先 verify |
| GET /api/log?svc=&lines= | 会话 | 末 N 行(默认 200,上限 1000) |
| POST /api/password | 会话+Origin | `{old_password,new_password≥8}` |

请求体统一 4MB 上限。错误统一 `{"error":"..."}`。

### 前端要点

- 登录框/主界面同页切换(以 `/api/status` 401/200 判定);状态 5s 轮询;日志手动+5s 自动(贴底自动滚)。
- 会话:登录响应的 `token` 存 `localStorage`(被分区/禁用时退化为内存,刷新需重登但不回环),每个请求带 `Authorization: Bearer`;401 时清 token 回登录页。
- `using_default_password`(登录响应与 `/api/status` 都有)为真时,主界面顶部显示琥珀色提醒条 + "现在修改"按钮,改完密码 `pollStatus()` 自动收起。
- 编辑器脏标记 + `beforeunload` 拦截;保存/重启的 verify 结果落横幅(绿/红)。
- 顶部显示 `frp v<上游版本>` 与 `管理壳 v<上游版本>`;完整包版本(x.y.z.构建号)看应用中心——**管理壳不维护构建号**(monorepo CI 里 build_num 在 workflow 另一步才算出,build.sh 拿不到,AppBuild 已删)。

## 三、打包与 project.yaml

### rootfs 布局

```
rootfs_common/  icon.png(256×256,<100KB,与 launcher/www/icon.png 同源,build.sh 有 cmp 断言)
                www/index.html  ← inner 形态的**真页面**(网关从这里静态 serve,不能放占位页)
                www/icon.png    ← 页内 /icon.png 图标
rootfs_<arch>/  bin/{frp-mgr, frpc, frps}   ← start_cmd 首段必须每个架构都有
```

⚠ `www/` 下这两份由 `build.sh` 每次构建时从 `launcher/www/` 覆盖同步(内嵌到二进制的那份才是唯一源),改了内嵌页面忘了拷是**必踩**的坑 —— 表现是"桌面打开还是旧界面"。
`launcher/www/index.html` 仍被 `go:embed` 打进二进制,用于直连 28600 的场景(本地开发/局域网直连),所以 `GET /`、`/icon.png`、`/favicon.ico` 由管理壳自己 serve。

### project.yaml 关键字段

- `start_cmd: bin/frp-mgr --port=28600` 与 `port: 28600` 必须一致(平台探活)。
- `proxy_path: api` + `open_type: inner`:网关只把 `/api/` 反代到 28600(不剥离前缀,后端路由本来就写成 `/api/xxx`),其余路径从 `www/` 静态提供。
- `supports: []`(平台默认写 app+pc;inner 在手机端会跳手机浏览器打开,可用);`tag_types: [utility]`。
- `permissions: [NETWORK.ACCESS_INTERNET]`;`depend_fw_version: 1.13.0.0000`。
- 合规字段:Apache-2.0 的 LICENSE/source/support 三链接;`publisher: atou`。
- ⚠ description 里不能出现"英文冒号+空格"(YAML mapping 坑),已全用中文标点。
- ⚠ `version` 中段最多两位(ugcli 隐藏校验);0.71.1 合规。

### 构建脚本(两份,别混)

| | 本目录 `scripts/build.sh`(归档) | monorepo `scripts/apps/frp/build.sh`(真身) |
|---|---|---|
| 契约 | 无参,自己算构建号(dist 最大+1) | `build.sh <version> <arch>`,CI 按架构 matrix 各调一次 |
| 版本注入 | -X main.AppVersion=0.71.1 固定 | -X main.AppVersion=$1(跟随上游) |
| 产物 | dist/ 本地 upk | apps/frp/.../build_dir/,只进 GitHub Release |
| 工具链 | 本机 go(GOTOOLCHAIN=local) | 现场下载钉死 go1.26.6(natfrp/dnet 同款) |

CI 侧职责链:`get-latest-version.sh`(上游最新版)→ `resolve-release-tag.sh`(tag 去重 + build_num=max(全 app tag 数,历史资产内构建号)+1)→ build.sh → CI sed project.yaml version → `ugcli check` → `pack --arch <arch> --build N` → release → catalog.yml 生成 apps.json。

- **native 应用 ugcli check 容忍单架构树**(实测),所以 build.sh 单架构组装即可;Docker 型才要求双架构齐。
- 构建号坑:`--build` 传十进制,`0014` 会被当八进制;`printf '%04d'` 补零只用于展示。

## 五、monorepo CI 操作手册

| 场景 | 操作 |
|---|---|
| 跟上游自动更新 | 零操作。frp 发稳定版 → schedule(每日 08:00 UTC)自动构建发版;同版本已发布则 tag 去重跳过 |
| 手动构建某版本 | Actions → Build UGOS Pro App Packages → dispatch,app=`frp`,version 留空取最新/填指定(如 `v0.72.0`) |
| 同版本重发(补丁) | dispatch 带 `revision`(如 `r2`)→ tag `frp/v0.71.1-r2`,构建号自动 +1 |
| push 触发 | 只动 `apps/frp/**` 或 `scripts/apps/frp/**` 即只构建 frp(!! `.md` 改动不触发);别 push 后紧接着 dispatch 同应用(撞 release tag) |
| 商店目录 | release 成功后 catalog.yml(workflow_run)自动刷 apps.json,bot 提交 `chore: refresh apps.json catalog [skip ci]`;本地推前先 `git pull --ff-only` |
| 推送纪律 | 只推 origin(GitHub) main;gitea 远端是未同步快照**勿推** |

上游 prerelease(-rc/-beta)不会被 `/releases/latest` 选中(get-latest-version.sh 注释说明),真要打用 dispatch 显式指定。

```bash
ssh -p 2022 claude@192.168.2.51                      # 测试盒
sudo tail -40 /volume1/@appstore/com.personal.atou.frp/log/com.personal.atou.frp.log  # 壳 stdout(systemd 重定向)
```

| 症状 | 判断 | 处置 |
|---|---|---|
| 启动即挂,日志一行 `fatal error: removed GODEBUG ...` | go1.27+ 二进制撞固件注入 | 壳已钉 1.26、子进程已消毒;若上游换工具链后仍见,查消毒是否被绕过 |
| frpc 反复"运行→退出" | loginFailExit,连不上/密钥错 | 看 frpc.log 最后一行;改对配置后重启 frpc |
| `token in login doesn't match` | frps 运行中改了配置不热加载 | 重启 frps(或两边 token 改一致后各重启一次) |
| 应用中心一直"启动失败" | 28600 被占/壳崩 | `ss -tlnp \| grep 28600`;查壳日志 |
| 首启参数/凭据行为怪 | 平台先起服务后写配置(unit BindPaths 晚 ~4s) | 等守护重启自愈;验证一律"重启后再看" |
| 商店不提示更新 | upk_version 逐段比较,构建号没升 | 核对 release 资产文件名里的构建号是否 > 已装 |

## 七、升级 frp 上游 checklist

1. 常规:什么都不做,等 schedule(或 dispatch)。上游发新版 → 自动出 `frp/v<new>` → catalog 自动刷新。
2. 上游改了 release 资产名/包内目录结构 → 改 `build.sh` 的 `ASSET`/`SRC_DIR`。
3. 上游大版本改动(配置格式破坏性变更) → 冒烟脚本里的样例配置要跟着改;必要时升 `depend_fw_version`。
4. 任何情况下发版前确认:ELF 断言过(check+pack 都会跑)、`frpc verify` 语义没变(冒烟用例 3)。

## 八、坑实录(全在本项目实测)

1. **默认模板 token 必须成对共享**:frps.toml/frpc.toml 各自随机生成 token → 出厂同时启用两边必 `token in login doesn't match`,且 frpc `loginFailExit` 退出陷入退避循环。修法:首启一次生成,两份模板共用。
2. **flx86(colima x86_64 VM)virtiofs 读取陈旧**:容器内读正被写入的日志文件,长期吐 NUL 垃圾段、新行不可见;Mac 侧与"稍后"才能读到。真机 ext4 无此层。tailLines 剔 NUL;冒烟日志断言锚定较早写入的壳事件行,登录成功用隧道回环断言权威证明。
3. **调试残留容器跨 VM 占同宿主端口 → 冒烟整片假 401**:两台 VM(colima/flx86)各自 `-p 28600` 会串台,curl 打到旧容器(密码不同 + 触发限流)。**判据:响应是"失败次数过多"而非"密码错误"必是串台**。开测前 `docker rm -f` 两台 VM 的同名容器。
4. **CI 里管理壳不显示构建号**:build_num 在 workflow 的 resolve-release-tag 步才算出,build.sh 拿不到;AppBuild 已删,壳只报上游版本,完整版本看应用中心。别再把 -X 注入构建号加回来。
5. **GODEBUG 平台注入**(见上):monorepo 巡检惯例——凡下载上游预编译 Go 二进制的应用,上游 bump 工具链那天可能全挂,发版前 `GODEBUG=tlskyber=0 ./binary --help` 反向验证。
6. **独立时期包与商店首发号的降级关系**:本机曾交付 0.71.1.0002(独立仓库构建),monorepo 首发是 0.71.1.0001(内容一致,构建号不同)。已装 0002 的话商店不会提示更新(也不需要),CI 后续发 0002+ 自然恢复更新链;UGOS 拦降级安装。
7. **⚠⚠ inner 白屏 ≠ 页面坏了:网关 https 口可能落在 Chromium「受限端口」上**(2026-11-07 真机,0.71.1.0003 首装):
   - 症状:桌面客户端开应用是**纯白窗口**(无报错、无滚动条),但同一时刻浏览器开 `http://NAS:<http口>/` 一切正常。
   - 根因:平台给 inner 应用分配**端口对**(本机是 10079 http / 10080 https),PC 客户端一律用 **https 那一侧**打开(客户端 profile 的 `Session Storage` 里全是 `https://NAS:100xx`)。而 Chromium/Electron 内置一张**受限端口表**(`net/base/port_util.cc` 的 `kRestrictedPorts`),含 10080(Amanda)、6000(X11)、6665-6669、6697、5060/5061 等 —— 命中就**在发请求前被拒**(`ERR_UNSAFE_PORT`),表现白屏,且不产生任何 session storage / 缓存记录。
   - 判据(不用碰 NAS):浏览器能开 `http://NAS:10079/`、`curl -k https://NAS:10080/` 也 200,但 Electron 白屏;本机可复现 —— 随便起个 `python3 -m http.server 10080`,浏览器开 `http://127.0.0.1:10080/` 同样白屏(curl 却 200)。
   - **端口对怎么来的**:ugcli 打包时 inner 应用的 config.json **不含** `baseAccessInfo.portInfo`(只有 `openType`),这对端口是**安装器在 NAS 上分配的**,落在 `/volume1/@appstore/<appid>/config.json`(`{port:100x, httpsPort:100x+1, httpsEnable:true}`),也从 NAS 的应用列表 API 原样回给客户端。分配规律实测是**共享池里取最低空格**:本机 40 个 inner 应用占 10001/10003/…/10081 成对排,而我们安装时 10081/10082 已被别的应用占着、却拿到 10079/10080(previous 应用卸载后留下的洞)——所以"卸载重装"大概率又回到同一个洞。`project.yaml` 没有任何字段能指定或关闭这对端口(`dynamic_port` 是另一回事:它只服务 `open_type: tab` + 空 `proxy_path` 的场景,让**应用自己的监听口**动态化,ugcli 会校验 `'port' cannot be set when 'dynamic_port' is configured`)。
   - 命中后只能让平台**重新分配**:卸载 → 先装任意另一个 inner 应用占住那个槽 → 再装本应用 → 拿到下一个空位(如 10083/10084);或找官方改这台机器上该应用的端口槽。
   - 反面教训:inner 改造光验"浏览器能打开"不够,**必须看桌面客户端那一侧**;客户端失败不留日志,浏览器对照 + 端口号即可定性。
